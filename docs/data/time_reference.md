# Time zones and reference times

`wetterdienst` returns every `timestamp` as `datetime[us, UTC]`, the same type for every provider and for values,
interpolated values and summaries; the provider tests hold the frame of every result they build to it. Providers do not publish that way. They stamp in UTC, in local civil time, in local
standard time or in a fixed offset, and they stamp the start, the end or the middle of the period an aggregate covers.
A mistake is an hour off, or a day at a daily boundary, and never an error, so this page records what each provider's
own documentation says and what the library does with it.

How to read the tables:

- **source time zone**: the zone in which the provider states its stamps.
- **reference time**: where the stamp sits in the period a value covers. `instant` is a reading at the stamp, `start`
  and `end` an aggregate over the period that begins or ends at it, `middle` one centred on it, and `mixed` that the
  datasets or parameters of the row differ (the qualifier says how). A daily stamp is a date at 00:00 UTC, so for it
  `start` and `end` say that the day's window begins or ends on that date, and the qualifier gives the window.
- **`unverified`** means the provider's documentation does not state it. The cell never holds a guess; where a
  comparison with a second source suggests an answer, the cell says so in brackets as an observation.
- **verified**: `yes` if the quoted text defines both zone and reference time as shown, `partly` if one of them rests on
  the stamp's format or the field names alone, `no` if the documentation says neither.
- The notes list, per row, what the library does with the stamp and the sentences of the provider the row rests on.
  German, French, Polish and Spanish quotations are given in the original.

A daily stamp is the date of the day it belongs to, at 00:00 UTC, for most providers, whatever window the provider
defines for that day (06:00 to 06:00 UTC for precipitation is common). The notes say where it is not.

Rows that deviate from their source are tracked as issues:

- [#2675](https://github.com/earthobservations/wetterdienst/issues/2675): stamped one hour early in the daylight-saving season
- [#2676](https://github.com/earthobservations/wetterdienst/issues/2676): `precipitation_amount_max` stamped one day early
- [#2677](https://github.com/earthobservations/wetterdienst/issues/2677): overseas departments are in the territory's own time, labelled UTC
- [#2678](https://github.com/earthobservations/wetterdienst/issues/2678): periods the source marks MEZ come back one hour late
- [#2679](https://github.com/earthobservations/wetterdienst/issues/2679): monthly stamps and months follow the request's start
- [#2680](https://github.com/earthobservations/wetterdienst/issues/2680): decade files chosen by the local year of the bounds
- [#2681](https://github.com/earthobservations/wetterdienst/issues/2681): request bounds sent as local wall-clock text
- [#2683](https://github.com/earthobservations/wetterdienst/issues/2683): a one-day request drops daily values not stamped at 00:00 UTC
- [#2682](https://github.com/earthobservations/wetterdienst/issues/2682): request bounds with a named time zone fail when the values are windowed

The type check on the `timestamp` column of every values result runs in each provider test (`tests/provider/conftest.py`).
